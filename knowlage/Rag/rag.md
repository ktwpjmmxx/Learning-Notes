# RAG（検索拡張生成）システム 学習メモ

## 1. RAGの内部システム：情報の取得プロセスとチャンキング
RAGのシステムは、大きく分けて**「インデックス化（事前の準備）」「検索（リトリーバル）」「生成（ジェネレーション）」**の3つのフェーズで構成されている。

### フェーズ①：インデックス化（Indexing）
- **チャンキング（Chunking）:** 外部ドキュメント（PDF、社内Wikiなど）を、意味の通る小さなテキストの塊（チャンク）に分割。
- **エンベディング（Embedding）:** 分割した各チャンクを、Embeddingモデル（テキストの意味を多次元ベクトル空間上の数値に変換するモデル）に入力し、ベクトルデータ化。
- **格納:** このベクトルデータと、元のテキストデータを「ベクトルデータベース」に保存。

####  チャンキングの仕組み（詳細）
- **LLMのトークナイゼーション：** BPE（Byte Pair Encoding）などのアルゴリズムを使い、「あらかじめ学習した辞書」と照らし合わせてテキストをIDに変換。
- **RAGのチャンキング：** 意味のある文章の「塊（ブロック）」を作るための処理です。用途に合わせて、以下のような条件（戦略）を指定してプログラムで切り分ける。
    - **固定長チャンキング（Fixed-size Chunking）：** 「500文字ごと」「オーバーラップ（重複部分）を50文字持たせる」といった文字数やトークン数による機械的な分割。
    - **構造的チャンキング（Structural Chunking）：** Markdownの見出し（`#` や `##`）、改行コード（`\n\n`）、HTMLタグなど、ドキュメントの構造を条件にして意味のまとまりごとに区切る。
    - **セマンティックチャンキング（Semantic Chunking）：** 近年注目されている手法で、文ごとの意味の類似度を計算し、話題が変わるタイミング（意味的な切れ目）を条件として動的にチャンクを分割。

### フェーズ②：検索（Retrieval）
- ユーザーが入力したプロンプト（質問）も、同じEmbeddingモデルを通ってベクトル化される。
- ベクトルデータベース内で、ユーザーの質問ベクトルと、保存されているドキュメントのベクトルの**「類似度（主にコサイン類似度）」**を計算し、意味的に近い（距離が近い）上位K件のチャンクを抽出する。

### フェーズ③：生成（Generation）
- 抽出されたチャンク（コンテキスト）と、ユーザーの元のプロンプトを結合し、LLMに渡す。
- LLMは「提供されたコンテキストに基づいて、以下の質問に答えなさい」という指示に従い、回答を生成。

## 2. プロンプト入力から生成までのチャンキングフロー
具体的な動作例として、社内規程のテキストを用いた一連のフローを確認。

### 【フェーズ1：事前の準備（インデックス化）】
1. **対象:** 「第5条：リモートワークは週3日を上限とする。ただし、育児や介護の事情がある場合は…」という社内規程のテキスト。
2. **チャンキング:** セマンティックチャンキング等により、上記のテキストが一つの意味の塊（チャンクA）として切り出される。
3. **エンベディング＆プーリング:** チャンクAがエンベディングモデルに入力され、プーリング処理を経て「リモートワークの条件」という意味を持つ1つのベクトル（例: `[0.1, -0.4, 0.8...]`）が生成される。
4. **格納:** ベクトルDBに、ベクトルと**生のテキストデータ（チャンクA）**が紐付いて保存される。

### 【フェーズ2：ユーザーの検索と生成】
1. **ユーザー入力:** ユーザーがプロンプトで 「リモートワークって週に何回までできる？」 と入力。
2. **プロンプトのエンベディング:** この質問文も、システム内部で事前の準備と全く同じエンベディングモデルとプーリング処理を通し、質問ベクトルに変換される。
3. **検索（リトリーバル）:** ベクトルDB内で、質問ベクトルと最も類似度が高い（距離が近い）ベクトルを探します。結果、チャンクAのベクトルがヒット。
4. **生データの抽出:** ヒットしたチャンクAのベクトルに紐づく**生のテキストデータ（「第5条：リモートワークは週3日を上限とする…」）**をデータベースから引き出す。
5. **LLMへの入力（プロンプト結合）:** RAGシステムは内部で以下のような最終プロンプトを動的に組み立て、LLM（生成モデル）に投げる。
   > 「以下の参考情報を用いて、ユーザーの質問に答えてください。
   > 参考情報：第5条：リモートワークは週3日を上限とする。ただし、育児や介護の事情がある場合は…
   > ユーザーの質問：リモートワークって週に何回までできる？」
6. **回答生成:** LLMが元のテキスト情報を読み込み、「社内規程によると、リモートワークは原則として週3日まで可能です。ただし…」という正確な回答をユーザーに出力。

## 3. 情報の精査：プロンプトに基づくフィルタリングと最適化
ユーザーのプロンプトに基づいて、システムがどのように情報を精査（フィルタリング・最適化）しているかが、RAGの精度を左右する最も重要な部分。

- **クエリ変換（Query Transformation）:**
  ユーザーの入力が検索に最適とは限らないため。システム内部で、ユーザーのプロンプトを検索しやすい形に書き換えたり（Query Rewriting）、複数のサブクエリに分解して網羅的に検索したりする処理が行われる。
- **メタデータフィルタリング（Metadata Filtering）:**
  ベクトル検索（意味的検索）の前に、「日付」「作成者」「カテゴリ」などのメタデータでハードフィルタリングをかける。これにより、例えば「2025年の最新の就業規則について」というプロンプトに対し、古い情報が混ざるのを防ぐ。
- **リランキング（Re-ranking / Cross-Encoder）:**
  ***情報の精査において最も強力な手法。*** ベクトル検索は計算が速い反面、文脈の細かいニュアンスを取りこぼすことがある。そこで、ベクトル検索で広めに拾ってきた上位数十件のドキュメントに対して、再評価（リランキング）モデルを通す。ユーザーのプロンプトと抽出した各ドキュメントを同時にモデルに入力し、「このドキュメントは本当にこの質問の答えとして適切か？」を精緻にスコアリングして並び替える。これにより、ノイズとなる情報を大幅に削減。

## 4. RAGの種類と特化した用途

- **① Naive RAG**
  - **仕組み:** 上記で説明した「チャンク化→ベクトル検索→生成」という最もシンプルな一方通行のパイプライン。
  - **用途:** シンプルな社内FAQボットや、単一のドキュメントに対するQA。
  - **課題:** 検索精度が低かったり、無関係なコンテキストを拾うとそのまま回答の精度が落ちる。

- **② Advanced RAG**
  - **仕組み:** Naive RAGの課題を克服するため、「検索前（クエリ変換やメタデータ付与）」「検索中（ハイブリッド検索：キーワード検索＋ベクトル検索）」「検索後（リランキングやコンテキストの圧縮）」の各段階に最適化のモジュールを組み込んだもの。
  - **用途:** 大規模な社内データベースの検索、より正確性が求められるカスタマーサポート、法務・財務ドキュメントの解析。

- **③ Modular RAG / Agentic RAG（エージェント型RAG）**
  - **仕組み:** 検索して生成するだけでなく、LLM自身が「検索結果が十分か」を評価し、足りなければ「別のキーワードで再検索する」というように、自律的にループやルーティングを行う手法（Self-RAGやCRAGなどが代表的）。
  - **用途:** 複雑な推論が必要なタスク、最新のWeb検索と社内データを組み合わせた動的なリサーチ業務。

- **④ GraphRAG**
  - **仕組み:** 情報を単なるテキストのベクトルではなく、エンティティ（人、会社、概念など）とその関係性をノードとエッジで結んだ「ナレッジグラフ」として構築・検索する手法。
  - **用途:** 「A社のCEOが過去に関わった別のプロジェクトは？」といった、複数の点と点を結びつけるマルチホップ推論が必要なタスク。医療データや金融ネットワークの分析に強力。
