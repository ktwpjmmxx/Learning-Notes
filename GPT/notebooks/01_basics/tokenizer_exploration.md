### 1. 各種トークナイザーの比較

同じ文章でもトークナイザーの種類によって分割のされ方が異なる。  
ここでは `"Is this world real ?"` を題材に、代表的な3種類を比較。

---

#### 🔹 BPE（Byte Pair Encoding, GPT-2 など）
- 仕組み  
  - 頻出する文字列のペアを統計的にまとめていくことで、単語をサブワード単位に分割する方式。  
  - 未知語も部分的に分割できるため、語彙外の単語に強い。  
- 分割例  

["Is", "Ġthis", "Ġworld", "Ġreal", "Ġ?"]

- `Ġ` はスペースを表すマーク。  
- 「スペース込みのトークン」として学習しているのが特徴。  

**メリット**
- 語彙外（OOV: Out Of Vocabulary）問題を回避しやすい  
- 未知語でも部分的に分割できるため柔軟  
- 実装が比較的シンプルで学習も高速  
- 英語などアルファベット系言語では効率的  

**デメリット**
- 言語依存性が高く、日本語や中国語では工夫が必要  
- 頻度ベースの分割で、意味的に不自然になる場合がある  
- サブワードが細かくなりすぎると文章が長くなり計算コスト増加 

---

#### 🔹 WordPiece（BERT など）
- 仕組み  
- BPE と似ているが、「確率的に最も尤もらしい分割」を選択する方式。  
- `[CLS]`, `[SEP]` などの特殊トークンを自動的に挿入するのも特徴。  
- 分割例  

["[CLS]", "is", "this", "world", "real", "?", "[SEP]"]

- `[CLS]`: 文全体を表すトークン。分類タスクなどに使用。  
- `[SEP]`: 文と文の区切りを表すトークン。  

**メリット**
- 確率的に最も尤もらしい分割を選ぶため自然な形になりやすい  
- `[CLS]`, `[SEP]`, `[MASK]` など特殊トークンを標準搭載  
- NLPタスク（分類・QAなど）で実績が豊富  

**デメリット**
- BPEより学習が複雑（尤度最大化の計算が必要）  
- 語彙サイズが大きくなりやすく、メモリコスト増加  
- GPT系のような生成タスクには不向きで、理解タスク向け

---

#### 🔹 SentencePiece（T5, GPT-NeoX など）
- 仕組み  
- 生テキストを直接扱い、空白も含めて符号化。  
- Unicodeベースで一貫して処理できるため多言語対応に強い。  
- 分割例  

["▁Is", "▁this", "▁world", "▁real", "▁?"]

- `▁` がスペースを表すマーク。  
- GPT-2 の `Ġ` と似ているが、こちらは SentencePiece 固有の表記。  

**メリット**
- 言語非依存で、多言語や分かち書きのない言語にも対応  
- Unicodeベースで記号や絵文字も処理可能  
- ライブラリが独立しており、語彙のカスタマイズが容易  

**デメリット**
- 分割結果が人間にとって直感的でない（`▁` など特殊記号）  
- 語彙設計次第で性能差が大きい  
- モデルによっては語彙サイズが大きくなりがち

---

#### 🔑 比較まとめ
- **BPE**：統計的に頻出するペアを結合。サブワードに強い。  
- **WordPiece**：尤度最大の分割を選ぶ。特殊トークンを活用する設計。  
- **SentencePiece**：Unicodeベース。多言語処理やカスタム学習に便利。


### 1-2. "Is this world real ?" を3種類のトークナイザーで比較

同じ文章でも、エンコード（文章 → トークンID）やデコード（トークンID → 文章）の結果はトークナイザーによって異なる。

---

#### 🔹 BPE（GPT-2）
- **エンコード**

["Is", "Ġthis", "Ġworld", "Ġreal", "Ġ?"]
→ [318, 922, 995, 1702, 30]

- **デコード**

"Is this world real ?"


特徴: `Ġ` はスペースを意味するマーク。スペース込みでトークン化されている。

---

#### 🔹 WordPiece（BERT）
- **エンコード**

["[CLS]", "is", "this", "world", "real", "?", "[SEP]"]
→ [101, 2003, 2023, 2088, 2613, 1029, 102]

- **デコード**

"is this world real ?"

※ `[CLS]`, `[SEP]` は特殊トークンで文章としては復元されない。

特徴: 特殊トークンを自動挿入。文構造や分類タスク用の補助的な役割を果たす。

---

#### 🔹 SentencePiece（T5など）
- **エンコード**

["▁Is", "▁this", "▁world", "▁real", "▁?"]
→ [156, 387, 921, 2021, 58]

- **デコード**

"Is this world real ?"


特徴: `▁` がスペースを意味するマーク。多言語に対応可能。

---

#### 🔑 まとめ
- **BPE**: サブワードに強い。スペースを `Ġ` として保持。  
- **WordPiece**: 文脈用の特殊トークンを自動追加。  
- **SentencePiece**: 言語非依存。スペースを `▁` として扱う。  

### 2. エンコード・デコード処理

テキストはそのままではニューラルネットワークに入力できないため、**数値（トークンIDの列）** に変換して扱う。  
この変換を行うのが **Tokenizer** 。

---

#### 🔹 2-1. エンコード処理（文章 → トークンID）

例: `"Is this world real ?"`

```python
from transformers import GPT2Tokenizer

tokenizer = GPT2Tokenizer.from_pretrained("gpt2")

text = "Is this world real ?"
encoded = tokenizer(text, return_tensors="pt")

print(encoded)

出力例:

{
  'input_ids': tensor([[318, 922, 995, 1702, 30]]),
  'attention_mask': tensor([[1, 1, 1, 1, 1]])
}
```

・input_ids: 各トークンを辞書（語彙）から引いたID列
・attention_mask: 「有効なトークン（1）」と「パディング（0）」を区別するマスク

🔹 2-2. モデル入力

エンコード結果をモデルに渡すと、ニューラルネットワークは次のトークンの予測を行う。

outputs = model.generate(encoded, max_length=20)

🔹 2-3. デコード処理（トークンID → 文章）

モデルが生成したトークン列を再び自然言語に戻す。

decoded = tokenizer.decode(outputs[0], skip_special_tokens=True)
print(decoded)

出力例:

"Is this world real ? Maybe it is, maybe it isn’t..."

・decode: ID列を人間が読める文字列に変換
・skip_special_tokens=True: [CLS], <PAD> などの特殊トークンを削除

**処理フローまとめ**

1. エンコード: テキスト → input_ids（数値化） + attention_mask
2. モデル処理: トークン列を入力し、次のトークンを予測
3. デコード: トークン列 → テキスト

モデルは「文章を理解 → 予測 → 人間に読める形に戻す」ことが可能になる。

### 2-4. input_ids と attention_mask の役割

#### input_ids
- **定義**: テキストを辞書から引いた「単語やサブワードのID列」
- **使い方**: 
  - モデル内部の埋め込み層（Embedding Layer）に入力される
  - 各IDは固定長ベクトル（例: 768次元）に変換され、数値的に扱えるようになる
- **例**
  "Is this world real ?" 
  → [318, 922, 995, 1702, 30]  
  → [[0.13, -0.27, ..., 0.04], ..., [...]]   # 埋め込みベクトル

#### attention_mask
- **定義**: 各トークンが「有効か無効か」を表すフラグ
  - 1 → 実際の入力として利用する
  - 0 → パディング（無視する部分）
- **使い方**:  
  Transformerの Self-Attention 計算時に利用される
  - 文章が短い場合 → バッチ処理のために `<PAD>` で長さを揃える
  - 余分な `<PAD>` 部分が計算に影響しないように mask で無視
- **例**
  input_ids      = [318, 922, 995, 1702, 30, 0, 0, 0]  
  attention_mask = [  1,   1,   1,    1,  1, 0, 0, 0]  

  → Self-Attention の計算では mask=0 の部分が無視される

#### まとめ
- **input_ids**: 文章を数値化してモデルに入力する主データ  
- **attention_mask**: どこまでが本物の文章かをモデルに教える補助データ  
- 短文・長文が混ざった入力でも、両者の組み合わせで正しく処理可能

### 3. 特殊トークンの扱い

自然言語処理モデルでは、文章中の通常の単語以外に **特殊トークン** が用いられます。  
これらはモデルの入力や出力の制御、タスクの補助に使われます。

---

#### 🔹 主な特殊トークンと役割

| トークン | 役割 | 使用例 |
|----------|------|--------|
| `<PAD>`  | パディング。文章の長さを揃える際に使用 | バッチ処理時の短い文章の末尾に追加 |
| `<UNK>`  | 未知語（語彙外トークン） | モデルの語彙に存在しない単語を表現 |
| `<CLS>`  | 文全体の特徴を表すトークン | BERT系の分類タスクで文章ベクトルの取得に使用 |
| `<SEP>`  | 文やセグメントの区切り | BERT系で複数文入力時に文の区切りとして使用 |
| `<EOS>`  | 文や文章の終了を表す | GPT系の生成タスクで文の終わりを認識させる |

---

#### 🔹 特殊トークンの使い方

1. **入力時**
   - `[CLS]` や `<EOS>` を文章の先頭・末尾に追加  
   - バッチ処理で `<PAD>` を末尾に追加  
   - モデルは attention_mask で `<PAD>` を無視

2. **出力時**
   - `<EOS>` を検出したら生成を停止  
   - デコード時に `skip_special_tokens=True` で取り除く

---

#### 🔹 BERT系とGPT系の違い

| モデル | 特殊トークンの主な使い方 |
|--------|-------------------------|
| BERT系 | `[CLS]` を文章全体表現に使用、`[SEP]` で文区切り、分類やQA向け |
| GPT系  | `<EOS>` で文章終了、生成タスクに特化。基本的に `[CLS]` は使わない |

---

#### 🔑 まとめ
- 特殊トークンは文章の構造やタスク仕様をモデルに伝えるための補助的トークン  
- デコード時には通常スキップされ、出力文章として現れない  
- BERT系は理解タスク向け、GPT系は生成タスク向けに設計されている
